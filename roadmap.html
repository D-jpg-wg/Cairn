О проекте · что это в итоге

Личная база знаний — сервис, куда стекаются заметки, ссылки, код-сниппеты и спарсенные статьи из разных источников (веб, бот, парсер), а затем находятся обратно — по тегу, по тексту или по смыслу.

Пользователь добавляет запись через веб, мобильный клиент или Telegram-бота. Parser в фоне подтягивает контент по расписанию (RSS, страницы по списку). Всё проходит через Main API, складывается в Postgres, индексируется для поиска и, на дальних фазах, превращается в embeddings для семантического поиска — «найди похожее по смыслу», а не только по точному совпадению слов.

Ключевая практическая цель — не сам продукт, а полигон: каждый сервис на роадмапе ниже добавляет повод пощупать конкретную технологию вживую, а не на туториале. Auth — это JWT и database-per-service. Kafka — события между сервисами. gRPC — синхронные внутренние вызовы с типизированным контрактом. Celery — фон внутри одного сервиса. Observability — как выглядит «сломалось» в системе из пяти сервисов, а не в монолите.

Пути передачи · кто с кем как говорит

Три разных пути для трёх разных задач: внешний трафик, внутренние вызовы, события.

Три пути

Веб, мобильный клиент и часть запросов бота идут через единый Gateway по обычному REST. Здесь живёт Swagger/OpenAPI, здесь проще всего дебажить через curl или Postman — это «человеческий» интерфейс системы, рассчитанный на внешних потребителей, не на скорость внутри кластера.

Используется там, где одному сервису нужен немедленный ответ от другого с заранее известной структурой данных: Bot Service дёргает Main API напрямую, Main API запрашивает у Search/ML топ похожих заметок. Контракт описан в .proto-файле, из него генерируется типизированный клиент и сервер на обоих концах — никакого ручного парсинга JSON.

Под капотом HTTP/2: можно делать не только unary-вызов (один запрос — один ответ), но и streaming — например, отдать пачку заметок на переиндексацию потоком, а не одним тяжёлым запросом.

protobufunarystreaminggrpcurl

Когда отправителю не важно, кто и когда прочитает событие и прочитает ли вообще прямо сейчас — это Kafka, а не gRPC. Main API публикует событие, Bot Service читает его асинхронно для уведомлений, Parser — для дозаписи новых данных. Связь по смыслу та же, что и в основной схеме архитектуры выше, просто здесь это один из трёх путей, а не вся картина целиком.

Важные моменты

gRPC — это синхронная связность: вызывающий сервис ждёт ответа и падает вместе с тем, кого вызвал, если не поставить таймаут. Если ответ не нужен немедленно («где-то потом обнови индекс») — это повод для Kafka, а не для ещё одного gRPC-вызова. Правило по умолчанию: нужен ответ прямо сейчас и для логики дальше — gRPC; можно подождать и неважно, кто и сколько раз прочитает — Kafka.

Номера полей в .proto — это контракт на проводе: новые поля добавлять можно, переиспользовать или удалять старый номер — нельзя, иначе старый и новый клиент начнут читать разные значения под одним именем.

На каждый gRPC-вызов нужен deadline. Без него зависший внутренний сервис подвешивает вызывающего, а тот — своего вызывающего, и зависание расползается по цепочке без единого упавшего лога.

Ретраи на стороне клиента (gRPC их умеет из коробки) означают, что вызов может прийти дважды — обработчик на стороне Main API должен быть идемпотентен, как и Kafka-консьюмер.

Браузер не умеет в HTTP/2-трейлеры, на которых держится gRPC, поэтому наружу — клиентам — gRPC напрямую не отдаётся. Если когда-нибудь захочется, чтобы веб-клиент дёргал внутренний сервис без посредника-REST, нужен отдельный мост — grpc-web или grpc-gateway, а не «просто открыть порт наружу».

Дорожная карта · фазы 0–8

Монорепозиторий с папкой на каждый сервис. Общий docker-compose.yml, чтобы поднимать всё разом локально. Линтер и pre-commit — лучше сразу, потом будет лень настраивать.

Идея продукта может быть размытой, но нужно зафиксировать минимум: кто пользователи и какие сущности — иначе не от чего оттолкнуться при проектировании Auth и Main API.

Auth-service на FastAPI: регистрация, логин, JWT с refresh-токенами, хэширование паролей. Своя БД только у него — database-per-service с первого дня.

Main API проверяет токены и реализует основную бизнес-логику. SQLAlchemy + Alembic в обоих сервисах. Цель фазы — не архитектура, а работающая связка из двух сервисов с тестами.

Redis + Celery в Main API — для отложенных и фоновых задач: письма, тяжёлые вычисления, периодика через Celery beat.

Kafka — шина событий между сервисами. Начни с одного события (например user.registered), не пытайся спроектировать все топики заранее.

Здесь же — первый .proto-контракт и первый gRPC-вызов между сервисами, пусть даже между Main API и заглушкой будущего Search-сервиса без реальной логики внутри. Цель фазы — пощупать сам механизм: кодогенерацию, deadline, grpcurl — а не сразу делать полноценный поиск. Подробнее о том, когда выбирать gRPC, а когда Kafka — в разделе «Пути передачи».

Технологии · что за что отвечает

Сервисы

REST API, валидация запросов через Pydantic, автодокументация (Swagger/OpenAPI) из коробки. Асинхронный — хорошо ложится на работу с Kafka и Celery.

Позволяет описывать таблицы и запросы на Python вместо сырого SQL на каждую операцию. У каждого сервиса — свои модели и своя сессия подключения к собственной БД.

Версионирует изменения схемы базы данных, позволяет накатывать и откатывать миграции. Работает в связке с моделями SQLAlchemy.

Асинхронная библиотека для Telegram-ботов с поддержкой FSM (машины состояний) для многошаговых диалогов.

Фреймворк для пауков: очереди запросов, обход страниц, экспорт данных. Запускается отдельно от основных сервисов, по расписанию.

Данные

database-per-service: никто не лезет в чужую схему напрямую, сервисы общаются только через API или события — это даёт независимость при изменении схемы.

Хранит очередь задач Celery и результаты их выполнения. Параллельно используется как быстрый кэш для часто запрашиваемых данных.

Связь и события

Продюсер пишет событие в топик, не зная, кто его читает. Consumer group у каждого сервиса-подписчика своя — копию события получают все подписчики независимо.

Ключ публикации (например user_id) определяет партицию и гарантирует порядок событий для одного пользователя. Доставка at-least-once — обработчики должны быть идемпотентны, событие может прийти дважды.

Не путать с Celery: Kafka — общение между сервисами, Celery — фоновые задачи внутри одного сервиса.

aiokafkatopicconsumer group

Выносит долгие операции из HTTP-запроса: отправка писем, тяжёлые вычисления, периодические job через Celery beat. Использует Redis как брокер.

Контракт описывается в .proto, из него кодогенерацией получается клиент и сервер на Python для обеих сторон — без ручного парсинга JSON и рассинхрона форматов между сервисами. Работает поверх HTTP/2.

Поддерживает не только unary-вызов (один запрос — один ответ), но и streaming в любую сторону — удобно для пакетной передачи данных между сервисами. Не путать с Kafka: gRPC — это синхронный вызов с ожиданием ответа, Kafka — публикация события без знания, кто и когда его прочитает.

Инфраструктура

Каждый сервис — свой контейнер. Compose поднимает весь стек локально одной командой — близко к тому, что будет в проде.

Деплой, автоматическое масштабирование, self-healing (перезапуск упавших подов). Приходит на смену docker-compose только на финальной фазе.

Принимает весь внешний трафик и маршрутизирует его к нужному сервису. Клиент видит один адрес, не зная о внутренней структуре системы.

Линт и тесты на каждый PR, сборка Docker-образов, пуш в registry, деплой при мерже в main.

Prometheus собирает метрики с сервисов (нагрузка, латентность, ошибки), Grafana строит по ним дашборды и алерты.

Собирает логи со всех сервисов в одно место с возможностью поиска — без этого в микросервисах придётся вручную ходить по контейнерам.
