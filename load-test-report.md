# Отчёт о нагрузочном тестировании микросервисов Cairn

**Дата:** 2 июля 2026
**Окружение:** все сервисы в Docker (Docker Desktop, macOS), нагрузка подавалась с хоста через проброшенные порты. Каждый HTTP/gRPC-сценарий — 20–30 секунд непрерывной нагрузки, если не указано иное.

В ходе тестирования были найдены и **сразу исправлены** три проблемы (пагинация, гонка тегов, пул соединений — подробности в разделе «Что нашли и починили»). Таблицы ниже показывают **текущее состояние системы после всех исправлений**.

## Инструменты

| Инструмент | Что делал |
|---|---|
| [ghz](https://ghz.sh) | нагрузка на gRPC-сервис `search`; схема из `proto/search/search.proto` (reflection на сервере не включён) |
| [hey](https://github.com/rakyll/hey) | нагрузка на HTTP-эндпоинты `auth` и `main-api` |
| [py-spy](https://github.com/benfred/py-spy) | семплирующий профайлер: раскладка CPU по функциям внутри процесса main-api под нагрузкой |
| `kafka-consumer-groups.sh` + логи | измерение лага consumer group и скорости разбора очереди у `link-enricher` (у сервиса нет портов) |

Для авторизованных сценариев используется тестовый пользователь `loadtest@example.com` (живёт в базе auth, можно переиспользовать). JWT передаётся как `Authorization: Bearer`; токен живёт 15 минут. Все создаваемые тестами записи после прогонов удаляются из базы.

## Текущее состояние системы

### 1. Сервис `auth` (FastAPI, порт 8000)

| Сценарий | Клиентов | Пропускная способность | p50 | p95 | p99 | Ошибок |
|---|---|---|---|---|---|---|
| Health-check (максимум транспорта) | 50 | **8 110 req/s** | 5.6 мс | 9.7 мс | 10.6 мс | 0 |
| Профиль по токену (`GET /auth/me`) | 50 | **1 413 req/s** | 33 мс | 75 мс | 106 мс | 0 |
| Логин (`POST /auth/login`) | 10 | защищён rate limit | — | — | — | — |

**Про логин:** эндпоинт ограничен **5 запросами в минуту с одного IP** (slowapi). Из 82 925 нагрузочных запросов прошло 5, остальные мгновенно получили `429 Too Many Requests` (сервер отбивал их со скоростью 2 764 req/s, не тратя CPU на bcrypt). Перебор паролей невозможен — это осознанная защита, а не узкое место.

**Про `/me`:** на каждый запрос — проверка RS256-подписи JWT + поход в Postgres за пользователем. Если когда-нибудь станет узким местом — кэшировать пользователя по uuid.

### 2. Сервис `main-api` (FastAPI, порт 8001)

Все сценарии — при 2 000 записях у пользователя.

| Сценарий | Клиентов | Пропускная способность | p50 | p99 | Ошибок |
|---|---|---|---|---|---|
| Health-check | 50 | **8 629 req/s** | — | — | 0 |
| Создание записи (`POST /entries/` → Postgres + Kafka) | 20 | **398 req/s** | 68 мс | 238 мс | 0 |
| Список записей (`GET /entries/`, пагинация по 50) | 50 | **404 req/s** | 114 мс | 272 мс | 0 |
| Список с фильтром, пустой результат | 50 | **988 req/s** | 43 мс | 163 мс | 0 |
| Семантический поиск (`GET /entries/search` → gRPC → `search`) | 50 | **2 774 req/s** | 17 мс | 53 мс | 0 |

Список отдаёт страницы по 50 записей (максимум 200 через `?limit=`). Создание записи — полный конвейер: валидация → вставка в Postgres (запись + upsert тегов через `ON CONFLICT`) → публикация события `entry.created` в Kafka. Межсервисная цепочка поиска (HTTP → gRPC) добавляет лишь ~10 мс к голому gRPC.

Пул соединений к Postgres: `pool_size=20, max_overflow=30, pool_pre_ping=True` — под пиковой нагрузкой открывается до ~50 соединений без ошибок.

### 3. Сервис `search` (Python + grpc.aio, gRPC, порт 50051)

Метод `search.v1.SearchService/Search` (unary). Реализация пока заглушка — цифры показывают потолок транспортного слоя, а не будущего векторного поиска.

| Сценарий | Клиентов | Пропускная способность | p50 | p95 | p99 | Ошибок |
|---|---|---|---|---|---|---|
| Лёгкая нагрузка | 10 | **7 081 req/s** | 1.3 мс | 2.1 мс | 2.5 мс | 0.005% |
| Средняя нагрузка | 50 | **6 562 req/s** | 6.6 мс | 10.5 мс | 11.3 мс | 0.025% |
| Стресс | 200 | **7 879 req/s** | 24.6 мс | 37.0 мс | 41.6 мс | 0.084% |

Потолок ~7–8 тыс. req/s достигается уже при 10 клиентах — предел одного Python-процесса (asyncio на одном ядре). Рост задержки при 200 клиентах — очередь перед насыщенным сервером, а не деградация. Все «ошибки» — обрывы TCP на границах теста. Память контейнера ~58 МБ.

### 4. Сервис `link-enricher` (Go, Kafka-консьюмер)

Сквозной тест конвейера: 2 000 записей типа `link` созданы через main-api → события `entry.created` в Kafka → enricher читает каждое и ходит по URL (в тесте URL вели на внутренний `http://auth:8000/api/v1/health`, чтобы не нагружать внешние сайты).

| Метрика | Значение |
|---|---|
| Обработано сообщений | 2 000 за ~7.1 с |
| Скорость разбора очереди | **~283 msg/s** (включая HTTP-запрос на каждое сообщение) |
| Лаг consumer group после теста | **0** — шёл вровень с производителем |

### 5. Совокупная нагрузка: все сервисы одновременно

30 секунд параллельной нагрузки на четыре сценария сразу (по 25 клиентов на каждый):

| Сценарий | В одиночку | Под общей нагрузкой | p99 |
|---|---|---|---|
| auth `GET /auth/me` | 1 413 req/s | **1 050 req/s** | 65 мс |
| main-api `GET /entries/` | ~410 req/s | **79 req/s** | 845 мс |
| main-api `GET /entries/search` (→ gRPC) | 2 774 req/s | **57 req/s** | 4.1 с |
| search gRPC напрямую | ~7 000 req/s | **7 024 req/s** | 5.6 мс |
| **Итого по системе** | — | **≈ 8 200 req/s** | |

Ошибок нет — все ответы 200/OK. Главный вывод: **узкое место системы — один Python-процесс main-api**: его эндпоинты делят одно ядро CPU, и под совместной нагрузкой лёгкие запросы поиска стоят в очереди событийного цикла за тяжёлой сериализацией списков. Auth и search, живущие в своих процессах, соседей не заметили. Рецепт масштабирования: несколько воркеров/реплик main-api за балансировщиком.

## Что нашли и починили в ходе тестирования

| # | Проблема | Было | Стало | Фикс |
|---|---|---|---|---|
| 1 | `GET /entries/` без пагинации: отдавал все записи разом (548 КБ JSON при 2 000 записях) | 18 req/s, p50 2.7 с | **404 req/s, p50 114 мс** (×23) | limit/offset в роутере → сервисе → репозитории; дефолт 50, максимум 200 |
| 2 | Гонка в `_get_or_create_tags`: параллельные запросы одновременно создавали один тег, проигравшие падали с 500 (`UniqueViolationError`) | 14 × HTTP 500 на 2 000 создании | **0 ошибок**, тег в базе один | `INSERT ... ON CONFLICT (name) DO NOTHING` + перечитывание — конфликт разрешает Postgres атомарно |
| 3 | Пул соединений SQLAlchemy (дефолт 5+10): при замедлении процесса запросы ждали соединение 30 с и падали, а треть CPU уходила на форматирование трейсбеков этих ошибок | 42 × `QueuePool limit reached`, ~34% CPU на логирование исключений | **0 ошибок пула** под теми же условиями; паразитная нагрузка исчезла из профиля | `pool_size=20, max_overflow=30, pool_pre_ping=True` в `create_async_engine` |

Как находили: №1 — нагрузка + контрольный эксперимент (пустая выборка дала 988 req/s → тормозила отдача, а не база); №2 — повторный прогон на чистой базе; №3 — профилирование py-spy под нагрузкой (флеймграфы до/после лежат в `profile-entries-list-before-fix.svg` и `profile-entries-list-after-fix.svg`).

Важные различия: фикс №1 поднял **скорость**, фиксы №2 и №3 подняли **устойчивость** — среднюю скорость они не меняют, но убирают ошибки и каскадные отказы под пиком. Синхронный движок Celery-воркера намеренно не трогали: у prefork-воркера одна задача на процесс, дефолтного пула достаточно.

## Оставшиеся рекомендации (по приоритету)

1. **Параллелизм в link-enricher** — сообщения обрабатываются строго по одному с таймаутом запроса 5 с: один медленный внешний сайт уронит конвейер с 283 до ~0.2 msg/s. Заготовка пула воркеров с семафором уже лежит закомментированной в `main.go`.
2. **Реплики main-api** — если понадобится больше ~400 req/s на тяжёлых эндпоинтах (см. совокупный тест). При нескольких репликах пересчитать бюджет соединений к Postgres (`max_connections=100` по умолчанию) или поставить PgBouncer.
3. Убрать `print(..., flush=True)` на каждый запрос в `search/app/grpc_server.py` — заменить на логгер.
4. Когда в `search` появится реальный векторный поиск — повторить тест: текущие цифры это потолок транспорта.
5. По профилю CPU у `GET /entries/`: ~50% — сборка ORM-объектов; следующий кандидат на ускорение — выборка только нужных колонок вместо полных сущностей.

## Как воспроизвести

```bash
# gRPC search
ghz --insecure --proto proto/search/search.proto \
  --call search.v1.SearchService.Search \
  -d '{"owner_id":"load-test-user","query":"тест","limit":10}' \
  -z 30s -c 50 localhost:50051

# токен (живёт 15 минут): залогиниться и взять cookie cairn_token
JWT=$(curl -s -i -X POST localhost:8000/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"loadtest@example.com","password":"LoadTest123!"}' \
  | grep -o 'cairn_token=[^;]*' | sed 's/cairn_token=//')

# HTTP-сценарии
hey -z 30s -c 50 http://localhost:8000/api/v1/health
hey -z 30s -c 50 -H "Authorization: Bearer $JWT" http://localhost:8000/api/v1/auth/me
hey -z 30s -c 50 -H "Authorization: Bearer $JWT" http://localhost:8001/api/v1/entries/
hey -n 2000 -c 20 -m POST -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $JWT" \
  -d '{"title":"Load test entry","type":"link","url":"http://auth:8000/api/v1/health","tags":["loadtest"]}' \
  http://localhost:8001/api/v1/entries/

# Лаг Kafka-консьюмера
docker exec cairn-kafka-1 /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group link-enricher

# Профилирование под нагрузкой (py-spy ставится в живой контейнер, пересборка его стирает)
docker exec cairn-main-api-1 pip install py-spy
docker exec --privileged cairn-main-api-1 /home/appuser/.local/bin/py-spy record \
  --pid 1 --duration 10 --rate 50 -o /tmp/profile.svg
docker cp cairn-main-api-1:/tmp/profile.svg ./profile.svg

# Чистка тестовых данных после прогонов
docker exec cairn-main-db-1 psql -U cairn -d cairn_main -c "
  DELETE FROM entry_tags WHERE entry_id IN (SELECT id FROM entries WHERE owner_id = 'c6f8da0b-be81-4324-befa-f0b1f709552e');
  DELETE FROM entries WHERE owner_id = 'c6f8da0b-be81-4324-befa-f0b1f709552e';
  DELETE FROM tags WHERE name = 'loadtest';"
```
