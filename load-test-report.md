# Отчёт о нагрузочном тестировании микросервисов Cairn

**Дата:** 2 июля 2026
**Окружение:** все сервисы в Docker (Docker Desktop, macOS), нагрузка подавалась с хоста через проброшенные порты. Каждый HTTP/gRPC-сценарий — 30 секунд непрерывной нагрузки, если не указано иное.

## Чем нагружали

| Инструмент | Что тестировал | Почему он |
|---|---|---|
| [ghz](https://ghz.sh) | gRPC-сервис `search` | стандартный CLI для нагрузки gRPC; схему брал из `proto/search/search.proto` (reflection на сервере не включён) |
| [hey](https://github.com/rakyll/hey) | HTTP-эндпоинты `auth` и `main-api` | лёгкий HTTP-генератор нагрузки (аналог ApacheBench, но честнее с keep-alive) |
| `kafka-consumer-groups.sh` + логи | `link-enricher` (Kafka-консьюмер) | у сервиса нет портов — измерял лаг consumer group и скорость разбора очереди |

Для авторизованных сценариев создан тестовый пользователь `loadtest@example.com` (остался в базе auth — можно переиспользовать). JWT передавался как `Authorization: Bearer`. Все созданные тестом записи (2 001 шт.) после теста удалены из базы.

## 1. Сервис `auth` (FastAPI, порт 8000)

| Сценарий | Клиентов | Пропускная способность | p50 | p95 | p99 | Результат |
|---|---|---|---|---|---|---|
| Health-check (максимум транспорта) | 50 | **8 110 req/s** | 5.6 мс | 9.7 мс | 10.6 мс | 243 328 × HTTP 200 |
| Логин (`POST /auth/login`) | 10 | — | — | — | — | **сработал rate limit** |
| Профиль по токену (`GET /auth/me`) | 50 | **1 413 req/s** | 33 мс | 75 мс | 106 мс | 42 418 × HTTP 200 |

**Про логин:** эндпоинт защищён лимитом **5 запросов в минуту с одного IP** (slowapi). Из 82 925 запросов прошло 5, остальные мгновенно получили `429 Too Many Requests` (сервер отбивал их со скоростью 2 764 req/s, не тратя CPU на bcrypt). Это отличная защита от перебора паролей — и именно поэтому «честно» нагрузить bcrypt снаружи нельзя.

**Про `/me`:** на каждый запрос — проверка RS256-подписи JWT + поход в Postgres за пользователем. 1.4 тыс. req/s с p99 около 100 мс — достойно; если станет узким местом, можно кэшировать пользователя по uuid.

## 2. Сервис `main-api` (FastAPI, порт 8001)

| Сценарий | Клиентов | Пропускная способность | p50 | p99 | Результат |
|---|---|---|---|---|---|
| Health-check | 50 | **8 629 req/s** | — | — | 258 906 × HTTP 200 |
| Создание записи (`POST /entries/`, 2 000 шт.) | 20 | **275 req/s** | 68 мс | 238 мс | 2 000 × HTTP 201 |
| Список записей (`GET /entries/`, 2 001 запись у пользователя) | 50 | **18 req/s** ⚠️ | 2.67 с | 9.35 с | 585 × HTTP 200 |
| Список с фильтром, пустой результат (`GET /entries/?q=...`) | 50 | **988 req/s** | 43 мс | 163 мс | 14 875 × HTTP 200 |
| Семантический поиск (`GET /entries/search` → gRPC → `search`) | 50 | **2 774 req/s** | 17 мс | 53 мс | 83 238 × HTTP 200 |

**Создание записи** — это полный конвейер: валидация → вставка в Postgres (запись + upsert тегов) → публикация события `entry.created` в Kafka. 275 req/s с p50 68 мс — рабочая цифра для write-пути.

**Главная находка — список записей без пагинации.** `GET /entries/` возвращал *все* записи пользователя разом: при 2 001 записи это 548 КБ JSON на каждый ответ, медиана 2.7 секунды, всего 18 req/s. Тот же эндпоинт с фильтром, отдающим пустой список, держит 988 req/s — то есть тормозила не база, а сериализация и отдача огромного ответа.

**Исправлено и перепроверено:** после добавления limit/offset-пагинации (по умолчанию 50 записей, максимум 200) тот же тест при тех же 2 000 записях у пользователя показал **415 req/s** (p50 108 мс, p99 384 мс, все ответы 200) — рост в **23 раза**.

**Бонус-находка при повторном прогоне:** гонка в `_get_or_create_tags` — при параллельном создании записей с одним и тем же новым тегом несколько запросов одновременно пытались создать тег, и проигравшие падали с 500 (`UniqueViolationError: ix_tags_name`). Из 2 000 параллельных созданий записей 14 получили 500.

**Исправлено и перепроверено:** конфликт перенесён в Postgres (`INSERT ... ON CONFLICT (name) DO NOTHING` + перечитывание). Контрольный прогон — 2 000 параллельных созданий записей с одним новым тегом: **2 000 × 201, ноль ошибок**, тег в базе ровно один. Пропускная способность записи — 398 req/s.

**Находка №3 (профилирование py-spy):** под 50 клиентами при замедлении процесса иссякал пул соединений SQLAlchemy (дефолт 5+10): запросы ждали соединение 30 секунд и падали с `QueuePool limit reached`, а треть CPU уходила на форматирование трейсбеков этих ошибок. **Исправлено:** `pool_size=20, max_overflow=30, pool_pre_ping=True` в `create_async_engine`. Перепроверено под теми же условиями (50 клиентов + профайлер, тормозящий процесс): под нагрузкой открывалось 52 соединения к Postgres, **ноль ошибок пула**; чистый прогон — 404 req/s, p99 272 мс, все ответы 200. Синхронный движок Celery-воркера не трогали намеренно: у prefork-воркера одна задача на процесс, дефолтного пула достаточно.

**Поиск через два сервиса** (HTTP → main-api → gRPC → search) держит 2 774 req/s с p50 17 мс — межсервисный вызов добавляет лишь ~10 мс к голому gRPC. Цепочка здоровая.

## 3. Сервис `search` (Python + grpc.aio, gRPC, порт 50051)

Метод `search.v1.SearchService/Search` (unary). Реализация пока заглушка — цифры показывают потолок транспортного слоя, а не будущего векторного поиска.

| Сценарий | Клиентов | Пропускная способность | p50 | p95 | p99 | Ошибок |
|---|---|---|---|---|---|---|
| Лёгкая нагрузка | 10 | **7 081 req/s** | 1.3 мс | 2.1 мс | 2.5 мс | 0.005% |
| Средняя нагрузка | 50 | **6 562 req/s** | 6.6 мс | 10.5 мс | 11.3 мс | 0.025% |
| Стресс | 200 | **7 879 req/s** | 24.6 мс | 37.0 мс | 41.6 мс | 0.084% |

Потолок ~7–8 тыс. req/s достигается уже при 10 клиентах — предел одного Python-процесса (asyncio на одном ядре). Рост задержки при 200 клиентах — это очередь перед насыщенным сервером, а не деградация: сервис под стрессом не ломается. Все ошибки — обрывы TCP на границах теста, не отказы логики. Память контейнера ~58 МБ.

## 4. Сервис `link-enricher` (Go, Kafka-консьюмер)

Тест конвейера: 2 000 записей типа `link` созданы через main-api → события `entry.created` ушли в Kafka → enricher прочитал каждое и сходил по URL (URL указывал на внутренний `http://auth:8000/api/v1/health`, чтобы не нагружать внешние сайты).

| Метрика | Значение |
|---|---|
| Обработано сообщений | 2 000 за ~7.1 с |
| Скорость разбора очереди | **~283 msg/s** (включая HTTP-запрос на каждое сообщение) |
| Лаг consumer group после теста | **0** — шёл вровень с производителем, очередь не копилась |

**Важная оговорка:** сервис обрабатывает сообщения строго по одному, а таймаут запроса — 5 секунд. С быстрыми внутренними URL это 283 msg/s, но один медленный внешний сайт затормозит весь конвейер до ~0.2 msg/s. Рекомендация: пул воркеров с ограничением параллелизма (заготовка с семафором уже лежит закомментированной в `main.go`).

## 5. Совокупная нагрузка: все сервисы одновременно

30 секунд параллельной нагрузки на четыре сценария сразу (по 25 клиентов на каждый), у пользователя 2 000 записей:

| Сценарий | В одиночку | Под общей нагрузкой | p50 | p99 |
|---|---|---|---|---|
| auth `GET /auth/me` | 1 413 req/s | **1 050 req/s** | 22 мс | 65 мс |
| main-api `GET /entries/` (с пагинацией) | 415 req/s | **79 req/s** | 295 мс | 845 мс |
| main-api `GET /entries/search` (→ gRPC) | 2 774 req/s | **57 req/s** | 209 мс | 4.1 с |
| search gRPC напрямую | ~7 000 req/s | **7 024 req/s** | 3.4 мс | 5.6 мс |
| **Итого по системе** | — | **≈ 8 200 req/s** | | |

Ошибок нет — все ответы 200/OK. Главный вывод: **узкое место всей системы — один Python-процесс main-api.** Когда два его тяжёлых эндпоинта нагружены одновременно, они делят одно ядро CPU: суммарно ~136 req/s, а поисковая цепочка, которая в одиночку давала 2 774 req/s, просела до 57 req/s с хвостом p99 в 4 секунды — запросы стоят в очереди событийного цикла за сериализацией списков. При этом auth и search, живущие в своих процессах, почти не заметили соседей. Рецепт масштабирования: несколько воркеров/реплик main-api за балансировщиком.

## Сводка и рекомендации

**Что хорошо:**
- Все сервисы стабильны под нагрузкой: ни одной 5xx-ошибки за весь тест (~900 тыс. запросов суммарно).
- Rate limit на логине реально работает и дёшево отбивает перебор.
- Межсервисная цепочка HTTP → gRPC добавляет лишь ~10 мс.
- Kafka-конвейер не копит лаг при 275 событиях/с.

**Что исправить (по приоритету):**
1. **Пагинация в `GET /entries/`** — сейчас это самое узкое место (18 req/s, полсекунды мегабайта JSON на ответ уже при 2 тыс. записей; дальше будет только хуже).
2. **Параллелизм в link-enricher** — один медленный внешний URL блокирует всю очередь.
3. Убрать `print(..., flush=True)` на каждый запрос в `search/app/grpc_server.py` — заменить на логгер.
4. Когда в `search` появится реальный векторный поиск — повторить тест (команды ниже воспроизводят всё за пару минут).

## Как воспроизвести

```bash
# gRPC search
ghz --insecure --proto proto/search/search.proto \
  --call search.v1.SearchService.Search \
  -d '{"owner_id":"load-test-user","query":"тест","limit":10}' \
  -z 30s -c 50 localhost:50051

# HTTP (токен: залогиниться loadtest@example.com и взять cookie cairn_token)
hey -z 30s -c 50 http://localhost:8000/api/v1/health
hey -z 30s -c 50 -H "Authorization: Bearer $JWT" http://localhost:8000/api/v1/auth/me
hey -z 30s -c 50 -H "Authorization: Bearer $JWT" http://localhost:8001/api/v1/entries/
hey -n 2000 -c 20 -m POST -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $JWT" \
  -d '{"title":"Load test entry","type":"link","url":"http://auth:8000/api/v1/health","tags":["loadtest"]}' \
  http://localhost:8001/api/v1/entries/

# Лаг Kafka-консьюмера
docker exec cairn-kafka-1 /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group link-enricher
```
